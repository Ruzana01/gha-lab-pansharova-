# Отчёт по лабораторной работе: GitHub Actions

## 1. Из каких элементов состоит workflow и как они вложены?
Workflow (YAML-файл в .github/workflows/) запускается событием (on).
Внутри него jobs, у каждого job есть runner (runs-on) и steps.
Step — это команда (run) или готовый action (uses).
Вложенность: workflow -> jobs -> steps.

## 2. Чем job отличается от step?
Job — набор шагов, который выполняется на одной отдельной виртуальной машине.
Jobs по умолчанию идут параллельно. Step — одна команда или action внутри job,
шаги идут по порядку на одной машине.

## 3. Чем запуск по push отличается от запуска кнопкой (workflow_dispatch)?
По push workflow запускается автоматически при каждом изменении в репозитории.
workflow_dispatch запускается вручную кнопкой Run workflow во вкладке Actions.

## 4. Как безопасно передать в workflow пароль или токен?
Через секреты: Settings -> Secrets and variables -> Actions -> New repository secret.
В workflow он используется как ${{ secrets.ИМЯ }}, а в логах скрыт (показывается ***).
Нельзя писать пароли прямо в YAML-файл.

## 5. Что такое артефакт и зачем он нужен?
Артефакт — файл, который job сохраняет после работы (upload-artifact).
Каждый job работает на отдельной чистой машине, поэтому артефакт нужен,
чтобы передать файл в другой job (download-artifact) или скачать результат.

## 6. Как заставить один job дождаться другого? Зачем нужен линтер, если есть тесты?
Через ключ needs: например, needs: build — job ждёт завершения build.
Без needs jobs идут параллельно (в эксперименте show падал, не найдя артефакт).
Тест проверяет, что код работает. Линтер проверяет качество и безопасность кода.
В лабе тест был зелёным, а shellcheck дал красный lint (SC2086: нужны кавычки
вокруг $1), потому что без кавычек скрипт ломается на пробелах и спецсимволах.
